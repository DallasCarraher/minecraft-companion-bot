Decision tick — what actually moves

One triggered chat line in, one chat reply out. The diagram is dataflow.squinch (interactive version: dataflow.html); the numbers below match the badges on it. Every payload here is the real shape from src/, filled with a plausible example — @bot go chop some wood.

Flow badges 1–15 = the cards on the right.

Trigger

1 Chat packet realm → mineflayer

The bot is a normal player, so it just receives chat. Mineflayer hands us two strings — no structure yet.

// bot.on('chat', (username, message) => ...)
"Dallas", "@bot go chop some wood"

2 Trigger gate chat/router.ts

Allowlist → record → trigger test → built-in commands → per-user cooldown → single-flight. Untriggered chat is still recorded as ambient context but never reaches the model; that plus the cooldown are the cost-control levers. 

{
  "username": "Dallas",
  "raw": "@bot go chop some wood",
  "triggered": true,           // chatTriggerMode: "mention"
  "strippedText": "go chop some wood",
  "builtinReply": null,          // "stop" / "status" / "help" would short-circuit here
  "cooldownMsRemaining": 0
}

3 ChatTurn → memory memory/store.ts

Appended to conversation, capped at the last 40 turns, then persisted with a 500 ms debounce and an atomic tmp-file rename. 

{
  "role": "user",
  "username": "Dallas",
  "text": "go chop some wood",
  "at": "2026-09-15T20:11:03.412Z"
}

4 runDecisionTick() llm/decisionLoop.ts

One tick owns one AbortController: "stop", a preempting tick, or a disconnect cancels it.

{
  "triggerMessage": { "role": "user", "username": "Dallas", "text": "go chop some wood", "at": "…" },
  "systemPrompt": "You are a helpful Minecraft companion…",  // static, cacheable
  "signal": "AbortSignal { aborted: false }",
  "say": "(msg) => void"  // immediate ack: "On it — working on that now."
}

Context assembly

Read fresh every tick, never persisted. Bounded on purpose: 16-block radius, 200 blocks sampled, 15 block types, 10 nearest entities.

Model turn

9 createTurn() request llm/providers/*.ts

system and tools[] are identical on every iteration and every tick, which is exactly why both adapters mark them cacheable. tools[] is the skill registry run through toolSchema.ts (filtered to what's relevant). 

{
  "system": "You are a helpful Minecraft companion…",
  "messages": [ { "role": "user", "text": "Chat from Dallas: …" } ],
  "tools": [
    {
      "name": "collectBlock",
      "description": "Mine and pick up the nearest blocks of a given type, up to a target count.",
      "jsonSchema": {
        "type": "object",
        "properties": {
          "blockName": { "type": "string", "description": "Block id, e.g. \"oak_log\", \"stone\", \"iron_ore\"" },
          "count": { "type": "integer", "minimum": 1, "maximum": 64, "default": 1 }
        },
        "required": ["blockName"],
        "additionalProperties": false
      }
    }
    /* … goToPlayer, craftItem, attackNearest, chestTransfer, … */
  ]
}

10 NormalizedResponse llm/types.ts

Both providers return this same shape. argsRaw is always a JSON string — the Anthropic adapter re-stringifies its already-parsed input so the loop never has to branch on provider. 

{
  "stopReason": "tool_calls",
  "text": null,
  "toolCalls": [
    { "id": "toolu_01A9cD", "name": "collectBlock", "argsRaw": "{\"blockName\":\"oak_log\",\"count\":10}" }
  ],
  "raw": "<provider response, kept for logging only>"
}

11 Args validation zod safeParse + repair.ts

Parse → validate against the skill's own schema. On failure the model gets one repair round-trip carrying the zod error; still bad and the tool result becomes an error the model can read. Repeated failures bump the model tier via modelRouter.ts. 

// success
{ "blockName": "oak_log", "count": 10 }

// failure path, what repair sends back to the model
{
  "failedCall": { "name": "collectBlock", "argsRaw": "{\"block\":\"oak\"}" },
  "validationError": "Unrecognized key: \"block\"; Required: blockName"
}

Action

12 SkillResult skills/gathering.ts

Runs under withTimeout(skill.timeoutMs, tickSignal) — 120 s for collectBlock. The skill reacts to the abort signal itself (bot.collectBlock.cancelTask()); the race is handled centrally. 

{ "ok": true, "message": "Collected 10x oak_log." }

// failure shape
{ "ok": false, "message": "Couldn't find any \"oak_log\" nearby." }

13 Tool result → messages[] the loop's only growing state

Pushed as a role: "tool" message, then the provider is called again with the longer messages[]. This is the loop: it repeats until the model stops asking for tools or the iteration cap is hit. 

[
  { "role": "user",      "text": "Chat from Dallas: …" },
  { "role": "assistant", "toolCalls": [{ "id": "toolu_01A9cD", "name": "collectBlock", "argsRaw": "{…}" }] },
  { "role": "tool",      "toolResults": [{ "toolCallId": "toolu_01A9cD", "content": "Collected 10x oak_log.", "isError": false }] }
  // → next iteration sends all three back, plus the same system + tools
]

Reply

14 Final turn stopReason: "end"

No tool calls this time, so the loop exits with the model's text as the reply.

{
  "stopReason": "end",
  "toolCalls": [],
  "text": "Collected 10x oak_log. Want me to drop them in the wood chest?"
}

15 Chat reply + write-back chat/format.ts → memory

Chunked to 240 characters on word boundaries (Minecraft truncates long lines), sent, and echoed back into conversation so the next tick sees what the bot said. 

// chunkChatMessage(replyText, 240)
["Collected 10x oak_log. Want me to drop them in the wood chest?"]

// appended to memory
{ "role": "assistant", "text": "Collected 10x oak_log. Want me to drop them in the wood chest?", "at": "2026-09-15T20:11:41.905Z" }

What survives

Persisted vs. rebuilt

Only the left column is on disk. Everything else is rebuilt from the live bot on the next tick — which is why a reconnect creates a new Bot and a new ChatRouter but keeps goals, tasks and known locations. 

// state.<realmId>.json  — survives restarts and reconnects
conversation · goal · taskQueue · knownLocations · playerPermissions · inventorySnapshot

// per tick, in memory only
DecisionContext · prompt message · messages[] · toolCalls · SkillResult · tool results

// per process, in memory only
AbortController (current tick) · per-user cooldown timestamps · system prompt · tool specs
