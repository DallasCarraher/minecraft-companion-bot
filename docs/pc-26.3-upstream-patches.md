# pc-26.3 upstream patches (temporary)

**Delete this file — and the `.yalc`/yalc-link setup it documents — once every PR below is merged
and released, and `package.json` is switched back to real registry versions of the five packages.**
Everything here is a stopgap for testing against Minecraft 26.3 before upstream support exists.

## Why this file exists

This project runs against yalc-linked local forks of five packages, patched in place to work with
26.3. None of the fixes are upstream yet. `bun install` (or anything that touches `node_modules`
without re-running `yalc push`) will silently wipe these patches and bring back the original
crashes — there is no other record of "why does this repo have five local forks" without this
file.

## Bug detail (what breaks, and why, if a patch is missing)

### 1. Realm auth race → `registerChannel is not a function`
Realm+Microsoft auth in `minecraft-protocol`'s `createClient.js` is async, but mineflayer's plugin
loader checks `client.wait_connect` synchronously right after `createClient()` returns. Without the
fix, plugin injection races ahead of the auth-completion callback (`onReady()`, which sets up
`registerChannel`), crashing immediately on connect — before any device-code prompt even appears.

### 2. `prismarine-physics` → `No liquid gravity settings, have you made sure the liquid gravity features are up to date?`
`prismarine-physics` hardcodes which MC versions support which liquid-gravity model in
`lib/features.json`. New point releases (26.2, then 26.3) aren't in that list until someone adds
them by hand — `Physics()` throws immediately on bot spawn otherwise.

### 3. Configuration-state packet ID drift → connection hangs forever (no crash, no error)
Mojang inserted a new `post_effects` packet at configuration-state ID `0x0a` in 26.3, shifting every
packet from `store_cookie` onward down by one ID slot in the wire protocol. `minecraft-data`'s table
didn't know about the shift, so the client misidentified `select_known_packs` as
`custom_report_details`, never sent the required response, and the server just... waits. Forever.
Steady `keep_alive` heartbeat, nothing else — the hardest of these bugs to diagnose because nothing
actually errors.

### 4. Play-state packet ID drift → garbage packet data, `bot.entity` never set, plugin crashes
Same class of bug as #3, much bigger: 144 clientbound + 69 serverbound play-state packets, all
shifted. Without the fix, the real `login`/join-game packet gets misread as something else entirely,
so `bot.entity` never gets initialized, and various mineflayer plugins throw trying to use it.

### 5. `prismarine-chunk` light-mask encoding → crash while loading the first chunk
26.3 changed the wire encoding of `ClientboundLightUpdatePacketData`'s bitmask fields
(`skyLightMask` etc.) from a varint-count-of-*longs* scheme to a varint-count-of-*bytes* scheme.
Without the fix, `ChunkColumn.js` throws in `loadParsedLight`/`readSection` because the light-section
array comes up short versus what the (correctly-parsed-as-longs, but wrong-scheme) mask claims.

### 6. Missing `tick_end` → kicked ~2s after every spawn (`invalid_player_movement`)
26.x added a new serverbound `tick_end` packet that real clients send once per tick. The server only
clears its "already received a position update this tick" flag on receiving `tick_end`. mineflayer
never sent one, so that flag latched `true` after the bot's first position packet and never cleared
— the *second* position-bearing packet sent over the whole connection (mineflayer's normal ~1s
keepalive resend) gets the bot kicked, regardless of how much time has passed.

### 7. Stepped entity-move delta encoding → console flooded with `PartialReadError` once other entities are nearby
26.3 replaced the old flat `dx/dy/dz` (3×`i16`) entity-movement delta encoding with a new
stepped/interpolated delta scheme, found live while actually playing near other entities on the
real Realm (a lone, stationary bot alone almost never triggers it). Three packets were affected,
each broken in its own way:

- **`rel_entity_move` / `entity_move_look`** (`ClientboundMoveEntityPacket`): the flat 3×`i16`
  delta is gone. It's now a packed `properties` varint (bit 0 = `onGround`, remaining bits =
  `stepCount`, i.e. `properties = (onGround?1:0) | (stepCount<<1)`) followed by either the old
  flat format when `stepCount <= 0` (still 3×`i16`, the common case when an entity's position was
  sent every tick — why this needed several nearby mobs/players to reproduce) or `stepCount`
  chained `{ticks: varint, dX, dY, dZ: i16}` steps, each relative to the position produced by the
  *previous* step, when the server batched several ticks of movement into one packet. Fixed with a
  new custom protodef type (`entityDelta` in `node-minecraft-protocol`) since the step count is a
  runtime-derived value (`properties >>> 1`) that plain declarative protodef can't express.
- **`sync_entity_position`** (`ClientboundEntityPositionSyncPacket`): the old flat
  `x/y/z/dx/dy/dz` fields are gone entirely. `position` is now a `PositionPath`: a varint type
  discriminator (0 = `Linear`, one absolute `{x,y,z}` f64 position; 1 = `Stepped`, a
  varint-counted list of absolute `{x,y,z: f64, tickOffset: varint}` steps) — no more velocity
  field on the wire at all. Expressed declaratively via `mapper`+`switch`+`array`, no custom type
  needed.
- Beyond parsing: mineflayer's entity-tracking (`lib/plugins/entities.js`) needed updating to
  apply *every* step in a stepped packet in order, not just the first/last — otherwise entities
  parse fine but their tracked position silently drifts/jumps further from reality the more ticks
  the server batches together.

Root cause fully confirmed (not guessed) by decompiling `VecDelta`, `VecDelta$Stepped$DeltaStep`,
`ClientboundMoveEntityPacket` (`.Pos`/`.PosRot`), `PositionPath` (`.Linear`/`.Stepped`),
`PositionStep`, and their `STREAM_CODEC`s / `packProperties`/`unpackStepCount` helpers in the real
26.3 server jar. `entity_teleport` and `entity_look` were checked too (grepped every class
referencing `VecDelta`/`PositionPath` in the decompiled jar) and confirmed unaffected — only these
three packets use the new encoding.

### 8. `packet_advancements` x/y placed in the wrong spot → `PartialReadError`, string field expecting a size >1MB
A same-night earlier commit (part of bug #4's PR) correctly noticed that 26.3 advancement entries
now carry an x/y position pair, but put it in the wrong place: it appended `x`/`y` *inside* the
`Advancement` container (after `sendsTelemtryData`) while *also* leaving the pre-26.3 `xCord`/
`yCord` fields inside `displayData`. Every advancement entry then carried two extra floats that
aren't actually on the wire there, which threw off byte alignment for the rest of the packet —
first observed live as `PartialReadError: Read error for undefined : Missing characters in string,
found size is 70385 expected size was 1466025` (a `>1MB` "expected size" on a string field is the
signature of an earlier-field misread cascading downstream, not a real string length).

Root cause confirmed by decompiling `ClientboundUpdateAdvancementsPacket` and its full
`STREAM_CODEC` chain (`$PositionedAdvancement`, `AdvancementHolder`, `Advancement`, `DisplayInfo`,
`AdvancementRequirements`, `AdvancementProgress`, `CriterionProgress`) in the real 26.3 server jar:

- `ClientboundUpdateAdvancementsPacket.added` is a `List<PositionedAdvancement>`.
  `PositionedAdvancement.STREAM_CODEC = composite(AdvancementHolder, x: f32, y: f32)` — x and y are
  siblings of the advancement entry itself (i.e. siblings of `key`/`value` in the existing
  key-value-pair schema shape), not fields inside the `Advancement`/`value` container.
- `AdvancementHolder.STREAM_CODEC = composite(id: Identifier, value: Advancement)` — matches the
  existing `key`/`value` entry shape.
- `Advancement.STREAM_CODEC` only sends 4 fields on the wire: `parent` (optional Identifier),
  `display` (optional `DisplayInfo`), `requirements` (`AdvancementRequirements`),
  `sendsTelemetryEvent` (bool) — `rewards`/`criteria`/`name` are server-only and never serialized.
- `DisplayInfo.STREAM_CODEC` has **no x/y at all** (title, description, icon, type, a 32-bit flags
  int, optional background texture identifier) — the `xCord`/`yCord` fields inside `displayData`
  were stale leftovers from an older MC version's advancement-tree layout and don't exist on
  26.3's wire format.
- `AdvancementRequirements` (`array<array<string>>`), `AdvancementProgress`
  (`map<string, CriterionProgress>`), and `CriterionProgress` (`option<Instant>`) were all
  re-checked against their `STREAM_CODEC`s too and already matched the existing
  `requirements`/`progressMapping`/`criterionProgress` schema, so those were left alone.

Fix: removed `xCord`/`yCord` from inside `displayData`, and moved `x`/`y` out of the
`advancementMapping` entry's `value` container to be siblings of `key`/`value` at the entry level.

Verified with a schema-level round-trip test (`createSerializer`/`createDeserializer` from
`minecraft-protocol`, serialize a sample `advancements` packet through the fixed schema then
deserialize it back) — the packet buffer is now fully consumed with no `PartialReadError`. Full
live-connection verification (local server + real Realm, triggering real advancements like
`minecraft:story/root` on first join) was originally blocked by the `recipe_book_add` `IDSet` bug,
which has since been fixed (see #10). A live check later showed the schema fix alone was not enough:
the packet still failed on a decorated-pot advancement icon because of a second, unrelated bug in
`SlotComponentType`/`pot_decorations` (see #14). With both fixed, the 72 KB `advancements` packet from a
real Realm decodes fully.

### 9. Stale `entities.json` pointer → bot can't recognize nearby players (`Can't see player "X" nearby`)
Found live in-game: telling the bot "follow me" while standing right next to it failed with
`Can't see player "X" nearby` even though a screenshot showed the bot and player adjacent. The
skill's `findPlayerEntity` (`src/skills/movement.ts`) requires `bot.players[username].entity` to be
set, which mineflayer's `lib/plugins/entities.js` only does once a `spawn_entity` packet's numeric
`type` resolves (via `entityDataByInternalId`, built from `bot.registry.entitiesArray`) to an entry
whose `type === 'player'`.

Root cause: `dataPaths.json`'s `pc["26.3"].entities` pointed at `"pc/26.1"` — two versions stale.
26.1→26.2 alone had already shifted 28 entity `internalId`s (including `player` 155→156) because new
entity types were inserted earlier in the registration order — the same "new things get inserted,
everything after shifts" pattern behind the packet-ID bugs (#3/#4). With the stale pointer, the
`internalId` mineflayer had on file for `player` didn't match what the 26.3 server actually sends on
the wire, so every player `spawn_entity` packet got misidentified as some other entity type,
`entity.type` never became `'player'`, and the player→entity link in `bot.players` never happened.

Confirmed 26.3 needed its own freshly-generated `entities.json` (not just a repoint to `pc/26.2`) by
decompiling `net.minecraft.world.entity.EntityTypes`'s static initializer in the 26.3 server jar via
`javap -c`: unlike `EntityTypeIds` (alphabetically-declared `ResourceKey` constants, not wire order),
`EntityTypes`'s static block calls `register(...)` for each entity type in a straight, branch-free
sequence (`static {}` — 0 `ifeq`/`ifne`/`goto` instructions), and the order those `putstatic`s appear
in *is* the order that assigns sequential numeric network IDs — 161 entries for 26.3, vs. 158 in
`pc/26.2`. Diffing the extracted order against `pc/26.2/entities.json` by name showed a clean,
insertion-only diff: exactly 3 new entities (`cushion`, `poplar_boat`, `poplar_chest_boat`), zero
removals, zero reordering elsewhere — `player` moves from `internalId` 156 (26.2) to 159 (26.3). The
new entities' dimensions/category were read from their own `EntityType.Builder` registration calls
in the same decompile (`poplar_boat`/`poplar_chest_boat` are structurally identical to `oak_boat`/
`oak_chest_boat`; `cushion` is a new sittable-furniture entity extending `BlockAttachedEntity`, width
1.0/height 0.25, `noLootTable`/`dontTrackDeltas`, with one extra synced field — `color`, a
`DyeColor` — read from `Cushion.defineSynchedData`'s bytecode).

Also audited the rest of the `pc["26.3"]` `dataPaths.json` row while in there: it turned out to be a
verbatim copy of the `pc["26.1"]` row with only `protocol`/`version` bumped — missing the whole wave
of updates `pc["26.2"]`'s row had already picked up from 26.1 (`attributes`, `blocks`, `items`,
`biomes`, `blockCollisionShapes`, `blockLoot`, `commands`, `entityLoot`, `foods`, `language`,
`loginPacket`, `materials`, `particles`, `recipes`, `sounds`, `tints`, `windows`). Repointed all of
those from `pc/26.1` to `pc/26.2` — a strict improvement (1-version-stale using already-known-good
26.2 data, vs. 2-versions-stale) that didn't require decompile-regenerating each one individually.
Left `effects`/`enchantments`/`instruments`/`mapIcons` alone since `pc["26.2"]`'s own row also keeps
those at their older pointers, suggesting that data is legitimately unchanged across 26.1/26.2/26.3.
`windows`: `1.16.1`→`1.20.3` (matching 26.2's row) was spot-checked by diffing both `windows.json`
files — the only change is an added `minecraft:crafter_3x3` window, a real (older) MC feature,
confirming the bump is safe.

Verified two ways:
1. **Locally**, spawning two bots against `local-test-server-26.3/` with plain mineflayer (no
   companion-bot skills involved) — `botOne.players['VerifyBotTwo'].entity` became set within a few
   seconds of both bots being connected, with `entity.type === 'player'`.
2. **Against the real Realm**, running the actual companion bot (`DEBUG=minecraft-protocol bun run
   dev`) with a temporary debug listener (removed before committing) on `playerUpdated`/`entitySpawn`
   — confirmed live: `{"username":"DarlaLamas","hasEntity":true,"entityType":"player"}` as soon as
   the real in-game player was nearby. (Unrelated `PartialReadError`s on `entity_metadata` also
   appeared in that run — that was the separate `entity_metadata` bug, since fixed in #10; it didn't
   block the player-entity link from working.)

`findPlayerEntity`/`followPlayer` in `src/skills/movement.ts` weren't touched — the bug was entirely
in the stale data, not the bot's own code.

### 10. `entityMetadataEntry`/`Particle` type-mapper drift + `SlotDisplay.tag` mistyped as string → `PartialReadError` on `packet_recipe_book_add`, size-mismatch on `entity_metadata`
> **Correction (see #14):** the first bullet below (`entityMetadataEntry` renumbering) is wrong. It
> followed declaration order, and the ids it produced (`block_state`=8, `boolean`=10, ...) do not match
> what 26.3 servers send. Use the order in #14. The `Particle` mapper and `SlotDisplay.tag` findings
> below are unaffected.

Found live via `DEBUG=minecraft-protocol` against both a real Realm and
`local-test-server-26.3/`: `packet_recipe_book_add` threw
`PartialReadError: Read error for undefined : Unexpected buffer end while
reading VarInt` on every connection (as soon as the player had at least one
craftable recipe), and `entity_metadata` occasionally logged `Chunk size is
18 but only 14 was read ; partial packet : {..."metadata":[...,{"key":10,
"type":"particles","value":[{"type":"sonic_boom"}]}]}`. Two independent
schema drifts, both confirmed by decompiling the real 26.3 server jar:

- **`entityMetadataEntry`'s own `type` mapper** (the `byte`/`int`/.../
  `particles`/... enum read right after each metadata entry's index byte)
  was the pre-26.3 ordering. Decompiling
  `net.minecraft.network.syncher.EntityDataSerializers`'s static
  initializer — specifically the sequence of `registerSerializer(...)` calls
  at the bottom, which is what actually assigns each serializer's numeric
  wire ID (declaration order alone isn't authoritative; the registration
  *call* order is) — shows `optional_uuid` was removed entirely in 26.3
  (replaced by a new `optional_living_entity_reference`, still wire-identical:
  a plain 16-byte `UUID`), and that `boolean`, `rotations`, `block_pos`,
  `optional_block_pos`, `direction`, `block_state`, `optional_block_state`,
  `particle`, and `particles` were all reshuffled around that removal. Fixed
  by renumbering all 44 entries per the decompiled registration order and
  adding `optional_living_entity_reference` (id 17) and a new `dye_color`
  (id 43, `ByteBufCodecs.idMapper` over `DyeColor` — wire-identical to a
  plain `varint`).
- **The shared `Particle` container's own `type` mapper** (used by both
  `entity_metadata`'s `particle`/`particles` fields *and*
  `packet_world_particles`) was also pre-26.3. Decompiling
  `net.minecraft.core.particles.ParticleTypes`'s static initializer the same
  way (its `register(name, ...)` call order against
  `BuiltInRegistries.PARTICLE_TYPE`) gives a longer, reshuffled 128-entry
  list (the old schema only had ~117): new `geyser`/`geyser_base`/
  `geyser_poof`/`geyser_plume`/`sulfur_bubbles`/`noxious_gas`/
  `noxious_gas_cloud`/`red_poplar_leaves`/`orange_poplar_leaves`/
  `yellow_poplar_leaves`/`sulfur_cube_goo` types were inserted, and
  `trial_spawner_detected_player(_ominous)` was renamed to
  `trial_spawner_detection(_ominous)`. `sonic_boom` moved from id 28 to 35;
  `note` moved from id 58 to 68 — meaning wire byte `58` (what a *real*
  `note` particle used to send) now means `vibration`, whose non-void payload
  (`positionType`/`position`/`ticks`) was being silently skipped as if it
  were `note`'s void data, corrupting every field after it. Fixed by
  rebuilding the full 128-entry mapper from the decompiled order and adding
  `data`-switch cases for the four new geyser variants
  (`GeyserParticleOptions.STREAM_CODEC` = `waterBlocks: i32` only;
  `GeyserBaseParticleOptions.STREAM_CODEC` — used by `geyser_base`/
  `geyser_poof`/`geyser_plume` — adds `burstImpulseBase: f32`).
- **`SlotDisplay`'s `tag` variant** (used inside `RecipeDisplay`'s
  `ingredients`, and reached from `packet_recipe_book_add` via
  `RecipeDisplayEntry.craftingRequirements`) was typed as a plain `string`
  (a bare tag name), but decompiling
  `SlotDisplay$TagSlotDisplay`'s `STREAM_CODEC` shows it's actually
  `ByteBufCodecs.holderSet(Registries.ITEM)` — the exact same
  `registryEntryHolderSet` (`IDSet`) encoding used everywhere else in the
  schema, not a bare string. This was the direct cause of the
  `packet_recipe_book_add` crash: a live capture of the raw packet bytes for
  a crafting-table recipe (`#minecraft:planks` tag, 4 identical ingredient
  slots) showed a `0x00` discriminator byte (`IDSet`'s "this is a named tag,
  not an explicit id list" case) immediately followed by the tag name
  string — but the old schema read that `0x00` as a *string length* (i.e. an
  empty string), then tried to re-read the *next* varint-length-prefixed
  string's length byte (`0x10` = 16, the real tag name's length) as an
  unrelated `SlotDisplay` type discriminator, which doesn't exist in the
  mapper (`16` isn't a valid `SlotDisplay` type) → garbage cascades from
  there until a `varint` read runs off the end of the buffer. Fixed by
  retyping `tag` from `"string"` to `"IDSet"`.

Both drifts were found and fixed together because they share underlying
mechanics with bug #9 (registration-order-vs-declaration-order matters, and
newer point releases insert entries that shift everything after them) and
because the `Particle` type is reused by both originally-reported bugs.

### 10b. `packet_world_particles` stale field layout → `Chunk size is N but only M was read` on every particle effect
Found live only *after* fixing #10's `Particle` mapper: with the corrected
mapper, `world_particles` packets started decoding a real `type` (e.g.
`vibration`, `note`) instead of a wrong one, which then exposed that the
packet's own field layout (`ClientboundLevelParticlesPacket`) was itself
stale pre-26.x: the old schema had `longDistance`/`alwaysShow`/`x`/`y`/`z`/
`offsetX`/`offsetY`/`offsetZ`/`velocityOffset`/`amount`(`i32`) followed by
`particle` *last*.

Decompiling `ClientboundLevelParticlesPacket`'s `STREAM_CODEC` (a 14-arg
`StreamCodec.composite(...)`) and its record field list shows the real 26.3
layout is completely different:

1. `particle` (`Particle`, dispatch-typed) — **first**, not last.
2. `overrideLimiter` (bool) — schema calls this `longDistance`, same wire
   position/type.
3. `alwaysShow` (bool)
4. `x`, `y`, `z` (`f64` each)
5. `xDist`, `yDist`, `zDist` (`f32` each) — schema's `offsetX`/`offsetY`/
   `offsetZ`.
6. `xMaxSpeed`, `yMaxSpeed`, `zMaxSpeed` (`f32` each) — **three new fields**
   replacing the old single `velocityOffset: f32`.
7. `count` (**`varint`**, not `i32`) — schema's `amount`.
8. `randomizationType` — a **brand new** trailing field, an enum
   (`ByteBufCodecs.idMapper`, i.e. wire-identical to `varint`) with 3 values:
   `default`/`alternative`/`alternative_with_speed`.

Fix: reordered `particle` to the front, renamed/added the three max-speed
floats, changed `amount` to `varint`, and appended the new
`randomizationType` mapper field.

Verified live against `local-test-server-26.3/`: issued `/particle`
commands for `note` (void data), `sonic_boom` (void data), and
`item{item:{id:"minecraft:diamond"}}` (non-void `ItemStackTemplate` data),
plus captured naturally-occurring `vibration` particles (emitted by nearby
mobs' warden-adjacent AI/sculk sensors) carrying a real
`{positionType:"entity", position:{entityId, entityEyeHeight}, ticks}`
payload — all parsed cleanly with sane coordinates and zero
`PartialReadError`/chunk-size-mismatch console spam across a multi-minute
session with several mobs (warden, sniffer, breeze, copper_golem, villager)
alive. `packet_recipe_book_add` was separately verified to correctly parse a
real crafting-table recipe (`#minecraft:planks` `IDSet` ingredient) end to
end.

### 11. `ItemBlockProperty.minValue`/`maxValue` mistyped as bare strings → stream desync kills the connection
Found live: the bot connected fine but crashed ~30s later with `Parse error
for play.toClient: Read error for undefined : array size is abnormally
large, not reading: 1919906932`, deep inside `ItemBlockPredicate` ->
`DataComponentMatchers` -> `SlotComponent` -> an NBT `longArray` read — the
signature of a field earlier in the same structure being misread, corrupting
everything downstream. This happened deterministically on every reconnect
(same garbage array-size value every time), and was initially assumed
non-fatal by analogy with earlier bugs that logged-and-recovered — it isn't:
the TCP socket ended up in `CLOSE_WAIT` shortly after, `spawn` never fired,
and the bot reconnect-crash-looped indefinitely. This is what was actually
breaking the bot mid-session, not the whisper feature that happened to be
added around the same time.

Decompiling `RangedMatcher`'s `STREAM_CODEC` (part of `BlockPredicate`,
referenced from `ItemBlockPredicate`'s block-property matching) shows
`minValue` and `maxValue` are each `ByteBufCodecs.optional(ByteBufCodecs.STRING_UTF8)`
— an optional, presence-prefixed string — not a bare required string. The
existing schema had both as plain `string`. Any open-ended range (only one
of min/max actually present — an ordinary case, e.g. a single-sided
waterlogged-state check) skips a presence byte that the old schema didn't
know to expect, throwing off every subsequent byte in the packet.

Fix: `minValue`/`maxValue` changed from `string` to `["option", "string"]`
in `ItemBlockProperty`.

Verified:
- Schema-level round trip (`createPacketBuffer`/`parsePacketBuffer` directly
  on `ItemBlockPredicate`): the old schema couldn't even *encode* a null
  min/max (crashed at `sizeOf` time); the fixed schema round-trips exactly
  for minValue-only, maxValue-only, and neither-present cases.
- Live against `local-test-server-26.3/`: gave items `can_place_on`/
  `can_break` predicates carrying an open-ended waterlogged range. Both the
  dropped item's `entity_metadata` and the inventory `set_slot` packet
  decoded cleanly (minValue present, maxValue key absent, as expected) with
  zero `PartialReadError` across the session — and, critically, confirmed
  the connection *stayed alive* well past the previously-fatal point:
  `map_chunk`/`entity_velocity`/`sound_effect`/`tick_end` kept flowing
  normally, `bot.entity` stayed set, and chat commands got normal server
  feedback, not just "the specific error stopped appearing."


### 14. `entityMetadataEntry` ids wrong (declaration vs registration order) + `SlotComponentType` shifted by 12 new components
Found with `PACKET_DEBUG=1 bun run dev` (see "Method"), which records every packet `protodef`
swallows. On a `PartialReadError` `FullPacketParser` only `console.log`s the stack and drops the
packet, so nothing reaches the `error` or `raw` events; capturing them needs the wrapper in
`src/mineflayer/packetDebug.ts`.

**(a) Entity metadata.** Symptoms: dozens of `PartialReadError`s at login, all in `packet_entity_metadata`
(`GlobalPos`/`Particle`/`VarInt` read errors), on both the Realm and `local-test-server-26.3`. The bytes
were readable only with a different table: villagers send `13 12 02 07 05 14 08 01` = key 19 `villager_data`
(type 18) then key 20 `boolean` (type 8). Key 6 is always the entity pose and arrived as type 20. #10 had
numbered `EntityDataSerializers` by *declaration* order (which includes helper fields such as
`SERIALIZERS` and `*_CODEC`); the wire ids follow the `registerSerializer(...)` *call* order. Extracted with
`javap -c -p` on `server-26.3.jar`, correct ids:

```
0 byte  1 int  2 long  3 float  4 string  5 component  6 optional_component  7 item_stack
8 boolean  9 rotations  10 block_pos  11 optional_block_pos  12 direction
13 optional_living_entity_reference  14 block_state  15 optional_block_state
16 particle  17 particles  18 villager_data  19 optional_unsigned_int  20 pose
21 cat_variant 22 cat_sound_variant 23 cow_variant 24 cow_sound_variant 25 wolf_variant
26 wolf_sound_variant 27 frog_variant 28 pig_variant 29 pig_sound_variant 30 chicken_variant
31 chicken_sound_variant 32 zombie_nautilus_variant 33 optional_global_pos 34 painting_variant
35 sniffer_state 36 armadillo_state 37 copper_golem_state 38 weathering_copper_golem_state
39 vector3 40 quaternion 41 resolvable_profile 42 humanoid_arm 43 dye_color
```

Why it went unnoticed: on a quiet local world only `float`/`int`/`byte`/`item_stack` entries appear, and a
`block_state`/`boolean` swap parses identically for one-byte values, so packets decoded "successfully"
with wrong types. Villagers (`villager_data`, `boolean`) on a populated Realm exposed it.

**(b) Data component ids.** The `advancements` packet (see #8) still failed after #8's fix, on an entry
whose icon was a decorated pot. `DataComponents` registers **122** components in 26.3; the schema's
`SlotComponentType` had 110, so every id from 40 on was off (component 76 is `pot_decorations`, the schema
said `block_state`). Fixed by reordering to the `register(...)` call order and adding:
`attack_animation`/`interact_animation` (both `SwingAnimation`), `cushion/color` (`varint`), `waxed`
(void), `sulfur_cube_content` (`ItemStackTemplate`), `villager_food`, `mob_visibility`
(`IDSet` + `f32`), `sign_text_front`/`sign_text_back` (two fixed 4-element `anonymousNbt` lists, colour,
glow flag); `map_color` removed. `pot_decorations` is `back/left/right/front`, each `option<ItemStackTemplate>`
(previously an array of ids). Field names for `villager_food` and `sign_text_*` are guesses; types and
order come from the bytecode.

**Known gap:** `block_transformer`, `compostable`, `cooking_fuel`, `brewing_fuel` and
`provides_pottery_pattern` have correct ids but no codec (they read as void), because they wrap loot
number providers (`ResolvableInt`/`ResolvableFloat`), `BlockTransformer` and `DecoratedPotPatterns`. An item
carrying one of these component types will desync the stream.

Verified: replaying the packets recorded by `PACKET_DEBUG` (379 packets incl. the 72 KB `advancements`)
through the fixed schema gives 0 parse errors and exact size matches; on the Realm the `entity_metadata`
`PartialReadError` flood stopped.

## Method used for all of the above

Every root cause here was found by decompiling the **official 26.3 server jar** (ships
deobfuscated) rather than guessing at wire formats from captured bytes:

```bash
unzip -q ~/Developer/mineflayer/server_jars/minecraft_server.26.3.jar "META-INF/versions/26.3/server-26.3.jar"
unzip -q "META-INF/versions/26.3/server-26.3.jar" -d server-classes
javap -cp server-classes -c -p <fully.qualified.ClassName>
```

Key classes referenced: `net.minecraft.network.protocol.configuration.ConfigurationProtocols`,
`net.minecraft.network.protocol.game.GameProtocols` (packet ID registration order — IDs are
assigned sequentially by `addPacket()` calls), `net.minecraft.network.protocol.common.ByteBufCodecs`
(bitmask wire format), `net.minecraft.server.network.ServerGamePacketListenerImpl` (movement
validation logic). This precedent was already established once before, for an earlier point release
(26.1.2): [mineflayer#3888](https://github.com/PrismarineJS/mineflayer/issues/3888).

A local throwaway offline-mode 26.3 server (`local-test-server-26.3/`, gitignored) was used to
diagnose bug #6, since it needed real server-side logs that a live Mojang Realm doesn't expose.
Same jar, run directly instead of decompiled.

**Capturing packets that `protodef` silently drops (#14).** Decompiling tells you the correct order;
this tells you *which* packets are wrong. `PACKET_DEBUG=1 bun run dev` writes JSONL to
`.scratch/packet-debug.jsonl` (gitignored): `dropped` lines carry the full hex of every packet that hit a
`PartialReadError`, and `raw` lines carry `entity_metadata` bytes (`PACKET_DEBUG_NAMES=a,b` or `all` for
others). Replay the file offline against the installed schema with `createDeserializer` from
`minecraft-protocol/src/transforms/serializer` to test a schema fix without a server. Registration order
for id-assigned registries (entity data serializers, data components) is the sequence of
`register...(...)` calls in the class's static initializer, *not* field declaration order:

```bash
javap -c -p -cp versions/26.3/server-26.3.jar net.minecraft.network.syncher.EntityDataSerializers
javap -c -p -cp versions/26.3/server-26.3.jar net.minecraft.core.component.DataComponents
```

After editing the data fork, republish it (`yalc publish` from `~/Developer/node-minecraft-data`, after
copying the changed file into its `minecraft-data/` submodule) and run `npx yalc update minecraft-data`
in this project; `yalc update` alone reads a stale store.
