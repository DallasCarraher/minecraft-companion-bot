# pc-26.3 upstream patches (temporary)

**Delete this file — and the `.yalc`/yalc-link setup it documents — once every PR below is merged
and released, and `package.json` is switched back to real registry versions of the five packages.**
Everything here is a stopgap for testing against Minecraft 26.3 before upstream support exists.

## Why this file exists

This project runs against yalc-linked local forks of five packages, patched in place to work with
26.3. None of the fixes are upstream yet. `bun install` (or anything that touches `node_modules`
without re-running `yalc push`) will silently wipe these patches and bring back the original
crashes — there is no other record of "why does this repo have five local forks" without this
file.

## Bug detail (what breaks, and why, if a patch is missing)

### 1. Realm auth race → `registerChannel is not a function`
Realm+Microsoft auth in `minecraft-protocol`'s `createClient.js` is async, but mineflayer's plugin
loader checks `client.wait_connect` synchronously right after `createClient()` returns. Without the
fix, plugin injection races ahead of the auth-completion callback (`onReady()`, which sets up
`registerChannel`), crashing immediately on connect — before any device-code prompt even appears.

### 2. `prismarine-physics` → `No liquid gravity settings, have you made sure the liquid gravity features are up to date?`
`prismarine-physics` hardcodes which MC versions support which liquid-gravity model in
`lib/features.json`. New point releases (26.2, then 26.3) aren't in that list until someone adds
them by hand — `Physics()` throws immediately on bot spawn otherwise.

### 3. Configuration-state packet ID drift → connection hangs forever (no crash, no error)
Mojang inserted a new `post_effects` packet at configuration-state ID `0x0a` in 26.3, shifting every
packet from `store_cookie` onward down by one ID slot in the wire protocol. `minecraft-data`'s table
didn't know about the shift, so the client misidentified `select_known_packs` as
`custom_report_details`, never sent the required response, and the server just... waits. Forever.
Steady `keep_alive` heartbeat, nothing else — the hardest of these bugs to diagnose because nothing
actually errors.

### 4. Play-state packet ID drift → garbage packet data, `bot.entity` never set, plugin crashes
Same class of bug as #3, much bigger: 144 clientbound + 69 serverbound play-state packets, all
shifted. Without the fix, the real `login`/join-game packet gets misread as something else entirely,
so `bot.entity` never gets initialized, and various mineflayer plugins throw trying to use it.

### 5. `prismarine-chunk` light-mask encoding → crash while loading the first chunk
26.3 changed the wire encoding of `ClientboundLightUpdatePacketData`'s bitmask fields
(`skyLightMask` etc.) from a varint-count-of-*longs* scheme to a varint-count-of-*bytes* scheme.
Without the fix, `ChunkColumn.js` throws in `loadParsedLight`/`readSection` because the light-section
array comes up short versus what the (correctly-parsed-as-longs, but wrong-scheme) mask claims.

### 6. Missing `tick_end` → kicked ~2s after every spawn (`invalid_player_movement`)
26.x added a new serverbound `tick_end` packet that real clients send once per tick. The server only
clears its "already received a position update this tick" flag on receiving `tick_end`. mineflayer
never sent one, so that flag latched `true` after the bot's first position packet and never cleared
— the *second* position-bearing packet sent over the whole connection (mineflayer's normal ~1s
keepalive resend) gets the bot kicked, regardless of how much time has passed.

### 7. Stepped entity-move delta encoding → console flooded with `PartialReadError` once other entities are nearby
26.3 replaced the old flat `dx/dy/dz` (3×`i16`) entity-movement delta encoding with a new
stepped/interpolated delta scheme, found live while actually playing near other entities on the
real Realm (a lone, stationary bot alone almost never triggers it). Three packets were affected,
each broken in its own way:

- **`rel_entity_move` / `entity_move_look`** (`ClientboundMoveEntityPacket`): the flat 3×`i16`
  delta is gone. It's now a packed `properties` varint (bit 0 = `onGround`, remaining bits =
  `stepCount`, i.e. `properties = (onGround?1:0) | (stepCount<<1)`) followed by either the old
  flat format when `stepCount <= 0` (still 3×`i16`, the common case when an entity's position was
  sent every tick — why this needed several nearby mobs/players to reproduce) or `stepCount`
  chained `{ticks: varint, dX, dY, dZ: i16}` steps, each relative to the position produced by the
  *previous* step, when the server batched several ticks of movement into one packet. Fixed with a
  new custom protodef type (`entityDelta` in `node-minecraft-protocol`) since the step count is a
  runtime-derived value (`properties >>> 1`) that plain declarative protodef can't express.
- **`sync_entity_position`** (`ClientboundEntityPositionSyncPacket`): the old flat
  `x/y/z/dx/dy/dz` fields are gone entirely. `position` is now a `PositionPath`: a varint type
  discriminator (0 = `Linear`, one absolute `{x,y,z}` f64 position; 1 = `Stepped`, a
  varint-counted list of absolute `{x,y,z: f64, tickOffset: varint}` steps) — no more velocity
  field on the wire at all. Expressed declaratively via `mapper`+`switch`+`array`, no custom type
  needed.
- Beyond parsing: mineflayer's entity-tracking (`lib/plugins/entities.js`) needed updating to
  apply *every* step in a stepped packet in order, not just the first/last — otherwise entities
  parse fine but their tracked position silently drifts/jumps further from reality the more ticks
  the server batches together.

Root cause fully confirmed (not guessed) by decompiling `VecDelta`, `VecDelta$Stepped$DeltaStep`,
`ClientboundMoveEntityPacket` (`.Pos`/`.PosRot`), `PositionPath` (`.Linear`/`.Stepped`),
`PositionStep`, and their `STREAM_CODEC`s / `packProperties`/`unpackStepCount` helpers in the real
26.3 server jar. `entity_teleport` and `entity_look` were checked too (grepped every class
referencing `VecDelta`/`PositionPath` in the decompiled jar) and confirmed unaffected — only these
three packets use the new encoding.

### 8. `packet_advancements` x/y placed in the wrong spot → `PartialReadError`, string field expecting a size >1MB
A same-night earlier commit (part of bug #4's PR) correctly noticed that 26.3 advancement entries
now carry an x/y position pair, but put it in the wrong place: it appended `x`/`y` *inside* the
`Advancement` container (after `sendsTelemtryData`) while *also* leaving the pre-26.3 `xCord`/
`yCord` fields inside `displayData`. Every advancement entry then carried two extra floats that
aren't actually on the wire there, which threw off byte alignment for the rest of the packet —
first observed live as `PartialReadError: Read error for undefined : Missing characters in string,
found size is 70385 expected size was 1466025` (a `>1MB` "expected size" on a string field is the
signature of an earlier-field misread cascading downstream, not a real string length).

Root cause confirmed by decompiling `ClientboundUpdateAdvancementsPacket` and its full
`STREAM_CODEC` chain (`$PositionedAdvancement`, `AdvancementHolder`, `Advancement`, `DisplayInfo`,
`AdvancementRequirements`, `AdvancementProgress`, `CriterionProgress`) in the real 26.3 server jar:

- `ClientboundUpdateAdvancementsPacket.added` is a `List<PositionedAdvancement>`.
  `PositionedAdvancement.STREAM_CODEC = composite(AdvancementHolder, x: f32, y: f32)` — x and y are
  siblings of the advancement entry itself (i.e. siblings of `key`/`value` in the existing
  key-value-pair schema shape), not fields inside the `Advancement`/`value` container.
- `AdvancementHolder.STREAM_CODEC = composite(id: Identifier, value: Advancement)` — matches the
  existing `key`/`value` entry shape.
- `Advancement.STREAM_CODEC` only sends 4 fields on the wire: `parent` (optional Identifier),
  `display` (optional `DisplayInfo`), `requirements` (`AdvancementRequirements`),
  `sendsTelemetryEvent` (bool) — `rewards`/`criteria`/`name` are server-only and never serialized.
- `DisplayInfo.STREAM_CODEC` has **no x/y at all** (title, description, icon, type, a 32-bit flags
  int, optional background texture identifier) — the `xCord`/`yCord` fields inside `displayData`
  were stale leftovers from an older MC version's advancement-tree layout and don't exist on
  26.3's wire format.
- `AdvancementRequirements` (`array<array<string>>`), `AdvancementProgress`
  (`map<string, CriterionProgress>`), and `CriterionProgress` (`option<Instant>`) were all
  re-checked against their `STREAM_CODEC`s too and already matched the existing
  `requirements`/`progressMapping`/`criterionProgress` schema, so those were left alone.

Fix: removed `xCord`/`yCord` from inside `displayData`, and moved `x`/`y` out of the
`advancementMapping` entry's `value` container to be siblings of `key`/`value` at the entry level.

Verified with a schema-level round-trip test (`createSerializer`/`createDeserializer` from
`minecraft-protocol`, serialize a sample `advancements` packet through the fixed schema then
deserialize it back) — the packet buffer is now fully consumed with no `PartialReadError`. Full
live-connection verification (local server + real Realm, triggering real advancements like
`minecraft:story/root` on first join) is blocked for now by the separate, concurrently-being-fixed
`recipe_book_add` `IDSet` parsing bug (tracked in the same PR/branch): it throws earlier in the
packet stream on every connection attempt right now, desyncing the byte stream for every packet
after it, including `advancements`, regardless of this fix. Will re-verify live once that lands.

### 9. Stale `entities.json` pointer → bot can't recognize nearby players (`Can't see player "X" nearby`)
Found live in-game: telling the bot "follow me" while standing right next to it failed with
`Can't see player "X" nearby` even though a screenshot showed the bot and player adjacent. The
skill's `findPlayerEntity` (`src/skills/movement.ts`) requires `bot.players[username].entity` to be
set, which mineflayer's `lib/plugins/entities.js` only does once a `spawn_entity` packet's numeric
`type` resolves (via `entityDataByInternalId`, built from `bot.registry.entitiesArray`) to an entry
whose `type === 'player'`.

Root cause: `dataPaths.json`'s `pc["26.3"].entities` pointed at `"pc/26.1"` — two versions stale.
26.1→26.2 alone had already shifted 28 entity `internalId`s (including `player` 155→156) because new
entity types were inserted earlier in the registration order — the same "new things get inserted,
everything after shifts" pattern behind the packet-ID bugs (#3/#4). With the stale pointer, the
`internalId` mineflayer had on file for `player` didn't match what the 26.3 server actually sends on
the wire, so every player `spawn_entity` packet got misidentified as some other entity type,
`entity.type` never became `'player'`, and the player→entity link in `bot.players` never happened.

Confirmed 26.3 needed its own freshly-generated `entities.json` (not just a repoint to `pc/26.2`) by
decompiling `net.minecraft.world.entity.EntityTypes`'s static initializer in the 26.3 server jar via
`javap -c`: unlike `EntityTypeIds` (alphabetically-declared `ResourceKey` constants, not wire order),
`EntityTypes`'s static block calls `register(...)` for each entity type in a straight, branch-free
sequence (`static {}` — 0 `ifeq`/`ifne`/`goto` instructions), and the order those `putstatic`s appear
in *is* the order that assigns sequential numeric network IDs — 161 entries for 26.3, vs. 158 in
`pc/26.2`. Diffing the extracted order against `pc/26.2/entities.json` by name showed a clean,
insertion-only diff: exactly 3 new entities (`cushion`, `poplar_boat`, `poplar_chest_boat`), zero
removals, zero reordering elsewhere — `player` moves from `internalId` 156 (26.2) to 159 (26.3). The
new entities' dimensions/category were read from their own `EntityType.Builder` registration calls
in the same decompile (`poplar_boat`/`poplar_chest_boat` are structurally identical to `oak_boat`/
`oak_chest_boat`; `cushion` is a new sittable-furniture entity extending `BlockAttachedEntity`, width
1.0/height 0.25, `noLootTable`/`dontTrackDeltas`, with one extra synced field — `color`, a
`DyeColor` — read from `Cushion.defineSynchedData`'s bytecode).

Also audited the rest of the `pc["26.3"]` `dataPaths.json` row while in there: it turned out to be a
verbatim copy of the `pc["26.1"]` row with only `protocol`/`version` bumped — missing the whole wave
of updates `pc["26.2"]`'s row had already picked up from 26.1 (`attributes`, `blocks`, `items`,
`biomes`, `blockCollisionShapes`, `blockLoot`, `commands`, `entityLoot`, `foods`, `language`,
`loginPacket`, `materials`, `particles`, `recipes`, `sounds`, `tints`, `windows`). Repointed all of
those from `pc/26.1` to `pc/26.2` — a strict improvement (1-version-stale using already-known-good
26.2 data, vs. 2-versions-stale) that didn't require decompile-regenerating each one individually.
Left `effects`/`enchantments`/`instruments`/`mapIcons` alone since `pc["26.2"]`'s own row also keeps
those at their older pointers, suggesting that data is legitimately unchanged across 26.1/26.2/26.3.
`windows`: `1.16.1`→`1.20.3` (matching 26.2's row) was spot-checked by diffing both `windows.json`
files — the only change is an added `minecraft:crafter_3x3` window, a real (older) MC feature,
confirming the bump is safe.

Verified two ways:
1. **Locally**, spawning two bots against `local-test-server-26.3/` with plain mineflayer (no
   companion-bot skills involved) — `botOne.players['VerifyBotTwo'].entity` became set within a few
   seconds of both bots being connected, with `entity.type === 'player'`.
2. **Against the real Realm**, running the actual companion bot (`DEBUG=minecraft-protocol bun run
   dev`) with a temporary debug listener (removed before committing) on `playerUpdated`/`entitySpawn`
   — confirmed live: `{"username":"DarlaLamas","hasEntity":true,"entityType":"player"}` as soon as
   the real in-game player was nearby. (Unrelated `PartialReadError`s on `entity_metadata` also
   appeared in that run — that's the separate, concurrently-being-fixed `entity_metadata` bug, not
   this one; it didn't block the player-entity link from working.)

`findPlayerEntity`/`followPlayer` in `src/skills/movement.ts` weren't touched — the bug was entirely
in the stale data, not the bot's own code.

## Method used for all of the above

Every root cause here was found by decompiling the **official 26.3 server jar** (ships
deobfuscated) rather than guessing at wire formats from captured bytes:

```bash
unzip -q ~/Developer/mineflayer/server_jars/minecraft_server.26.3.jar "META-INF/versions/26.3/server-26.3.jar"
unzip -q "META-INF/versions/26.3/server-26.3.jar" -d server-classes
javap -cp server-classes -c -p <fully.qualified.ClassName>
```

Key classes referenced: `net.minecraft.network.protocol.configuration.ConfigurationProtocols`,
`net.minecraft.network.protocol.game.GameProtocols` (packet ID registration order — IDs are
assigned sequentially by `addPacket()` calls), `net.minecraft.network.protocol.common.ByteBufCodecs`
(bitmask wire format), `net.minecraft.server.network.ServerGamePacketListenerImpl` (movement
validation logic). This precedent was already established once before, for an earlier point release
(26.1.2): [mineflayer#3888](https://github.com/PrismarineJS/mineflayer/issues/3888).

A local throwaway offline-mode 26.3 server (`local-test-server-26.3/`, gitignored) was used to
diagnose bug #6, since it needed real server-side logs that a live Mojang Realm doesn't expose.
Same jar, run directly instead of decompiled.
